# Observer source binding repair, v0.5.136

The original `j3n-01` attempt passed the 120-second admission window (121.461 seconds), then failed in the observer before a single sample: it read `source.json["source_sha256"]`, while the fixed descriptor uses `fixed_source_sha256`. The observer terminated its model child; recorded child exit is -15 and observed frames are zero. This is an acceptance-tool failure, not a completed smoke or evidence of model throughput. Original control bytes, admission, reports and logs are retained in `old-control/` and `j3n-terminal/`; the external originals are unchanged.

The fresh `j3p-control` requires the one canonical source key and binds it to the exact expected hash passed by the runner. The observer validates it before creating a run or starting a child. Runner, observer, static preflight and log-budget reader share the lightweight `source_identity.py`; the frozen support inventory is now 17 files, not the old 16. Missing, wrong-name, malformed, mismatching and ambiguous alias identities are rejected rather than accepted through a fallback. No Rust binary, city workload, threshold, fixture, clock protocol or frozen v132 input was changed.

Root validation passed 18 Python tests, the full fixed-source static preflight, all 17 support hashes, and three actual subprocess cases. Missing startup identity and a mismatching identity exited nonzero before creating their run roots. With the correct identity, the actual fixed Rust executable's intentional `--report-fault` path reported `metrics_unknown_class` and exited 2; the observer recorded `clock peer exited` and returned nonzero. That verifies the corrected startup/error path only: a successful model-clock handshake, sample collection, smoke and endurance were not proved by this negative case.

The first root validation used the wrong spelling for the expected fault diagnostic; its assertion failure and all raw outputs remain under `root-validation-01/`. The corrected distinct validation is `root-validation-02/`. The Rust output and observer were not altered to satisfy that assertion.

The new control's fresh roots are `j3p-01` (smoke) and `j3q-01` (formal); neither existed at this publication freeze. Both alias/resolved socket paths remain within the original Unix socket limit. A new smoke must pass the original admission, complete workload and persisted log-budget gate before formal may launch. The prior source or prior smoke does not grant this control a pass. See `verification.json`, `control/support-manifest.json` and the root validation receipts.
