# Spatial geometry revision candidate handoff

This batch adds a candidate builder in `city-map::geometry_revision`; it is not a Store update, permission grant, calendar action, or completed F acceptance. A later Engine/Store integration must approve and publish the candidate atomically before it can affect traffic or settlement.

## Candidate contract

`build_candidate` takes the exact prior `scene::Input`, the already-imported current and neighbor terrain, the current `traffic_adapter::AdapterInput`, the existing `TransportAllocationProfile`, its exact original bytes, and one `GeometryEdit`. It accepts either a changed quadratic road control point (start and end remain fixed) or one door, anchor, or terminal clear-width change. It increments `geometry_revision`, rebuilds the Scene through `Scene::assemble`, adapts both the prior and candidate Scene with the same IDs, OD rows, direction and facility settings, recomputes the assignment and profile, and returns exact candidate profile bytes and SHA-256.

The returned values include prior/candidate Scene hashes and adapter-configuration hashes, prior raw-profile hash, candidate-profile hash, terrain hashes, served people and per-edge free-flow seconds. Every effective edit increments the Scene geometry revision and the transport Opening revision independently from their own parent values; the candidate rejects overflow and does not require the two parent counters to match. The candidate retains only the candidate Scene, its exact allocation-profile bytes and compact summaries; it does not retain duplicate Opening/Assignment/TransportProfile graphs. `candidate_owned_capacity_bytes` reports the retained Rust-owned capacity represented by those fields, excluding allocator metadata and temporary assembly/serialization peak. It is a measurement hook, not a performance pass. This makes a dimension-only change visible even when it leaves the abstract transport profile unchanged. A wider corridor does not create capacity; facility capacity and speed remain copied from the explicit adapter config.

## Rejection and authority boundary

All existing Scene checks remain authoritative: terrain revision and datum, region and holes, flat support, building and obstacle clearance, connector endpoint continuity, road/anchor endpoint continuity, seam direction/width, layer, coordinates and current WALK-only mode. The adapter also continues to require its terminal point at the road start, matching ground elevation, enough clear width, explicit directional permission and authorization. Scene vector/string limits, transport graph/assignment limits and the maximum raw profile byte length are checked before cloning or decoding caller-supplied data. Baseline profile bytes must decode to the supplied validated profile; their exact raw SHA-256 is retained even when valid JSON whitespace differs.

This API makes no ownership or legal decision. A future writer must bind the candidate to the immutable source Scene/terrain identity, current geometry revision, affected asset and exact candidate hashes. Before publication it needs owner consent for affected private parcels/structures, the appropriate permit authority for road/port works, and consent/permit for the adjacent map port when a seam width or endpoint changes. It must reject stale revisions and candidates whose land footprint or connection rights exceed those approved. Only the writer can publish an approved candidate and its new geometry/profile references together.

The initial API intentionally does not edit road start/end, parcel footprint, seam ports, terrain, construction status, road capacity, modes, IDs, OD demand, ownership, or permits. There is no geometry mutation transaction, Store persistence, proof migration, or clock advancement here.

## Next integration seam

The finite CLI source is `crates/city-map/examples/geometry_revision_candidate.rs`. It uses the pinned synthetic `m0-spatial.json` and flat 16-bit terrain fixture, creates the baseline through the existing adapter, applies one valid curve or door-width edit, and writes full candidate Scene input, allocation-profile bytes, and a diagnostic/resource report to a caller-specified fresh output directory. Its output explicitly says `candidate_only_not_activated`; it does not write to Store, permissions, or calendar. It reports exact fixture/profile hashes, parent and candidate geometry/transport revision counters, per-edge travel seconds, served people, retained owned-capacity estimate, model wall time, and actual output logical bytes. The CLI has source only so far and is not counted as built or run until its command is executed and the output artifacts are inspected. Root will consolidate verified implementation and validation results into existing Issue #25.

The future writer should accept a candidate only after re-reading its parent Scene, terrain and profile bytes from the active immutable references, verifying the parent hashes and geometry revision, then applying the separately journaled owner/permit approvals. It should store the full candidate Scene and allocation profile as immutable assets and switch their active pointers in the same committed Engine/Store operation. Historical traffic proofs continue to name their original profile hash. This candidate module does not implement that writer contract.

## Runtime activation boundary and next implementation batch

The current Store integration is for opening and restoring one existing access edge, not changing geometry. `SpatialPermissionCommand` and `SpatialUpdateRequest` in `city-core/src/spatial_transport_permissions.rs` authorize `Close`/`Restore` against one genesis-registered surface and edge; the request binds a candidate allocation-profile hash but has no candidate Scene hash or geometry revision. `Store::stage_spatial_transport_candidate` in `city-storage/src/lib.rs` accepts a proposed `Opening`, requires its transport revision to be the current revision plus one, and accepts exactly one `open`-bit transition on that managed edge. A curve candidate changes travel times and geometry revisions without changing an access bit, so it cannot pass that edge-change contract.

The existing commit boundary is the right publication point to extend. On successful `Apply`, `Persistence::append_inner` validates the candidate Engine permission state and grant, calls `prepare_spatial_apply_catalog`, stages immutable assets and the next catalog, then publishes the new catalog digest through the same Root update as the WAL-backed Engine receipt. Keep that single transaction and reuse its timeline-derived `effective_service_day`; do not add another Store, clock, or journal. Today `SpatialTransportVersionRecord` binds an authorization witness and profile hash while the catalog keeps one fixed `source_scene_sha256`. `load_spatial_transport_catalog_on_open` checks that hash against the genesis `SpatialReference`, whose `spatial-input.json` and terrain files remain immutable. `town_transport::ArchivedProofRefs` resolves historical traffic proofs by the catalog's profile hash for their service day.

The geometry path needs these shared interfaces before a candidate can be activated:

- Extend the genesis permission policy and core request/grant witness with an explicit geometry-edit operation, affected spatial asset, expected parent Scene hash and geometry revision, exact candidate Scene raw-byte hash, candidate profile hash, and effective time. The authority context and owner/permit approvals must bind that exact request. The allowed geometry scope and affected ownership/permit accounts must come from Store-validated genesis policy; a CLI-supplied `authorized` flag or digest is not authority.
- Add one bounded Store candidate-validation/staging entry point that reads the exact candidate Scene bytes by their supplied hash, rebuilds it from the pinned terrain through `SpatialAssets`/`Scene::assemble`, and independently runs the adapter and allocation-profile checks. It must verify parent Scene/profile hashes and both independent parent revisions, keep endpoints, topology, OD demand, facility capacity/speed and approved property bounds fixed for this first edit, and reject invalid terrain support, collision, boundary escape, stale parents, or profile bytes not exactly derived from that Scene. Stage both immutable Scene and profile assets; staging alone still must not activate either.
- Extend the existing spatial version catalog so one version row binds previous and candidate Scene hashes/revisions together with previous and candidate profile hashes, authorization witness, effective service day, Engine operation ID, receipt revision and Store sequence. `append_inner`/`prepare_spatial_apply_catalog` must publish the consumed grant, new Scene/profile version and catalog digest only with the successful Root commit. On failure, staged blobs remain unreferenced and the prior Root and approvals remain authoritative.
- Extend cold-open/history validation from genesis: re-read the exact Scene and profile assets, replay each approved geometry transition and compare the final Engine permission state and active hashes. Preserve the old Scene/profile versions. Keep existing profile-by-service-day proof lookup unchanged for old proofs; add a parallel Scene-version resolver for active planning/inspection at a requested service day, using the same catalog boundary rather than a second clock.

The smallest useful next batch is one persistent-world integration test for a single existing WALK road with an in-bounds quadratic control-point move. It should use the real Store request, separate owner and permit approvals, a completed Timeline boundary, and the existing Apply commit path. Assert that the exact candidate Scene and profile hashes become active together; the accepted geometry and transport revisions each advance from their own parent; the travel-time-derived proof changes on the first effective service day while edge IDs, endpoints, direction, capacities, speeds, OD demand and served-population limits remain fixed; the prior day's proof still resolves to its old profile; and cold reopen plus exact replay restores the same active Scene/profile pair. Include specific rejections for missing approval, stale Scene parent, changed candidate bytes, out-of-bounds/collision geometry, and tampered catalog witness. This would connect the candidate to runtime activation; the current CLI and candidate-only tests do not meet that condition.
